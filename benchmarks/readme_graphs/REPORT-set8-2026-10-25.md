# VisualAgents README-graph check, set 8 (2026-10-25)

Ten agent projects that draw their agent graph in the README were scanned with `visualagents scan --static`. None of
them appears in sets 1-7 (70 projects). Each map was scored against the README graph. The failures were then traced
to code shapes the scanner did not understand, and those shapes were fixed with general rules on `dev-refinement`. No
rule names a project. All 70 projects of sets 1-7 were re-scanned before and after to check for regressions.

Ground truth is in `ground_truth_set8.py`. It was written from the README diagrams, and from the names the source uses
for each drawn box, before any scan. Raw scores are in `results-set8-2026-10-25.json`.

"Before" is `dev-refinement` at `d3d703a`, which is the set-7 work. It is not on `main` yet: it was handed off as a
bundle on 2026-10-24. "After" is this change, committed on top of it.

## How to read the numbers

- **Matching rate (node recall)**: the share of README components that appear on the map.
- **Correct rate (node precision, strict)**: the share of map blocks that are README components. The lenient version
  also accepts blocks that exist in today's code but are left out of the drawing, such as AgentVerse's simulation
  agents or Open Deep Research's tool-executor nodes.
- **Code recall**: the matching rate, leaving out drawn components that the code doesn't have as agents
  (`readme_only`). For example, ai-hedge-fund's portfolio, risk and execution boxes are plain functions since its
  2.x rewrite.
- **Edge recall / precision**: the share of README arrows found, and the share of map arrows that are README arrows.

## Differences per project, and why

**ai-hedge-fund.** This project was rewritten (2.x) after most write-ups about it. The README now draws a fund
engine:

> analysis → portfolio construction → risk checks → simulated execution → backtests

In today's code, only the analysis box uses a model: five persona analysts (`BuffettAgent`, `MungerAgent` … on an
`LLMAgent` base). These analysts are all on the map, so code recall is 1.0. The other four boxes are deterministic
functions: `blend_signals`, `apply_limits`, `execute_decision` and the backtester. A map of agents does not show
them, so all four README arrows are missed. This is a choice about what the tool draws, not a misread of the code.
See *Remaining failures*.

**Gemini fullstack quickstart.** Perfect before and after. It is a plain LangGraph `StateGraph` with `Send` fan-out.

**Open Deep Research.** All five components were found before and after. The one missed arrow (sub-agents →
supervisor) is drawn on the map:

> researcher → researcher_tools → compress_research → supervisor_tools → supervisor

The scorer only follows one code-only step between two README components, so it counts this arrow as missed. Strict
precision is 0.67 because the tool-executor and compression nodes are separate nodes in code. They are folded into the
boxes in the drawing.

**AgentVerse.** All four stages were found, from the task YAML configs. The loop back from evaluation to
recruitment was missed. The config allows several passes, but it names the limit `max_loop_rounds` (and in other
configs `max_turn: &max_turn 3`, a YAML anchor), and only `max_turns` / `max_rounds` were read. *Now* both are read, and
all arrows are found. Strict precision is 0.25 because the repository also ships the simulation side: a classroom, a
prisoner's dilemma, Pokémon town and others. Those are real code, so lenient precision is 0.97.

**Paper2Poster.** There were two separate problems:

- A copy of the CAMEL framework lives in the repository (`camel/`). Its own demo agents were on the map: role-playing
  pairs, a search agent, BabyAGI's task agents and others, 16 wrong blocks in all.
- The project builds its agents as local variables with the same names in many functions:
  `actor_agent = ChatAgent(...)` appears in `parse_raw()`, `gen_bullet_point_content()`, `deoverflow()` and more.
  All of these collapsed into one block, so the parser was lost and no pipeline order could be followed.

*Now*:

- The copied framework's agents leave the map.
- Each function's `actor_agent` / `critic_agent` is its own block.
- The run order is followed through `new_pipeline.py`. It also resolves `parse_raw` to the copy the file imports, not
  the one in `demo/`.

Edge precision is 0.60 because the pipeline's helper stages (deoverflow, theme) are drawn as extra arrows.

**AI-Researcher.** Two factories returned agents under the same literal name. `get_idea_agent()` was copied from the
survey factory and still says `Agent(name="Paper Survey Agent")`. So the idea generator merged into the survey agent.
Also, the flow class wraps each agent, as in `self.ml_agent = AgentModule(get_ml_agent(...))`. That made a second,
unlinked block for every wrapped agent.

*Now*:

- Copied factories are told apart by their function names.
- A wrapper attribute is the agent its factory builds.

The run order now goes:

> prepare → idea → code survey → coding plan → ML agent ⇄ judge, with ML agent ⇄ experiment analyser

The paper-writing composers are a separate pipeline of plain model calls (`GPTClient`). It runs in another mode of
the project, which uses framework agents elsewhere. That pipeline is still missing.

**Mobile-Agent-v2.** The whole system is one top-level script loop. It sends three prompts through one HTTP helper,
`inference_chat()`:

```python
output_action = inference_chat(chat_action, ...)
output_memory = inference_chat(chat_action, ...)
output_reflect = inference_chat(chat_reflect, ...)
output_planning = inference_chat(chat_planning, ...)
```

The memory call reuses the decision agent's conversation. Before, the helper itself was the only block. *Now* each
differently named prompt is a step. When two steps reuse one conversation, the reply variable names them. The script's
`while True` brings planning back to the action step. The one missed arrow (decision → reflection) runs through the
memory step on the map.

**MapCoder.** All four agents are model calls inside one method, `MapCoder.run_single_pass`:

- `input_kb_exemplars` is the retrieval agent;
- `input_for_problem_planning` and `input_for_planning_verification` are planning;
- `input_for_final_code_generation` is coding;
- `input_for_improving_code` is debugging.

Before, the class was one block. *Now* each is a step, in call order. Planning → coding is drawn through the
verification step, which the scorer counts as a duplicate planning block. The README's "back to planner" arrow is a
`for` loop over plans, not a round of one run, so it is not drawn. Strict precision is 0.40 because the other
prompting baselines (Direct, CoT, Analogical, SelfPlanning) are in the same package.

**AutoKaggle.** All five agents were found. Before, they were wired as a star around the planner, which was a guess
used when no order is known. The real order is data in `config.json`:

```json
{"phase_to_agents": {"Understand Background": ["Reader", "Reviewer"], "Data Cleaning": ["Planner", "Developer", "Reviewer", "Summarizer"], ...}}
```

*Now* each phase's list is a run order, and each phase follows the one before. The reader → planner arrow in the
README is reader → reviewer → planner in the config.

**OctoTools.** Before, the map showed the ten model-provider engines (`ChatOpenAI`, `ChatOllama`, `ChatVLLM` … under
`EngineLM`) as agents, and none of the framework's own components. The planner reaches a model only through
`self.llm_engine = create_llm_engine(...)` and then `self.llm_engine(prompt)`, which no name-based rule followed.

*Now*:

- Provider classes under one engine base are transport, not agents.
- A call on an object built by them, or by a factory of them, is a model call.
- The planner's prompted methods are steps, because `Solver.solve()` asks for them in turn: analyze_query →
  generate_next_step → executor → verificate_context ↺ → generate_final_output.

The command executor box is plain tool execution with no model call, so it stays off the map.

## Changes on dev-refinement (general rules, no project named)

1. **Prompt-variable steps** (`call_sites.py`). One function or script sends three or more differently named prompts
   through one model helper. Each prompt is a step, named after the prompt variable, or after the reply variable
   when two steps share a conversation. The steps are in call order, and a round-repeating loop goes back to the
   first. A script's top-level code qualifies too.
2. **Model backends are transport** (`call_sites.py`). Two or more provider-named classes under one project base, plus
   classes built on them, are never agents. Code that calls an object they or their factories build is the model
   call.
3. **Pipelines driven from outside** (`call_sites.py`). A class whose prompted methods a driver elsewhere calls in turn
   (three or more) is a pipeline of steps. A loop inside an agent that drives three or more others goes round.
4. **Phase lists in configs** (`static_scan.py`). These are JSON mappings of phase → list of agent names. They are
   used only when every name is a known agent and the code links none of them. A single list counts only under an
   order-like key.
5. **Copied factories and wrappers** (`static_scan.py`). Same-literal agents from differently named factories are
   named after the factories. `Wrapper(get_x_agent())` attributes alias the factory's agent.
6. **Copied frameworks** (`static_scan.py`). A framework package kept inside the repository (`camel/`, `autogen/` …)
   and imported by the project's own code keeps its agents off the map when the project has agents of its own. Not
   when the repository is that framework, and never the generic folder names `agents/` or `swarm/`.
7. **Role variables per function** (`static_scan.py`, `run_order.py`). A role-naming variable (not a bare `agent`)
   that holds a framework agent in two or more functions becomes one agent per function. Run order uses the
   function's own one. A call resolves to the copy of a function that its file imports.
8. **Turn limits under any name** (`static_scan.py`). This covers `max_*_rounds`, `*_turns`, `*_iterations` and
   `*_loops`, YAML anchors included, both with and without PyYAML installed.

Tests: `tests/test_scan_set8.py` adds 9 made-up projects, one or two per rule. The full suite passes (178 passed, 5
skipped).

## Remaining failures and likely causes

- **Non-agent pipeline boxes.** ai-hedge-fund's portfolio, risk and execution stages and OctoTools' command executor
  are deterministic code that the README draws next to the agents. The map shows only model-calling parts, so their
  arrows are lost. A possible next step is to draw functions that consume agent output in the same pipeline as
  passive steps, behind a flag to protect precision.
- **Mixed systems.** In AI-Researcher, plain-model-call code (the paper composers) sits beside framework agents. The
  plain-LLM pass runs only when no framework agents are found. Running it for this case without flooding other
  projects with helper calls needs a stricter gate.
- **Loops over planned items.** MapCoder's "debugging → back to planning" is a `for plan in plans` loop. It is
  deliberately not a round, because sets 6 and 7 showed that treating it as one adds wrong loop-back arrows.
- **Multi-product repositories.** AgentVerse's simulation side and MapCoder's baseline strategies keep strict precision
  low. They are real code, so lenient precision is 0.90-0.97.
- **Scorer reach.** An arrow drawn through more than one code-only step (Open Deep Research's sub-agents → supervisor)
  is on the map but scored as missed.
