# VisualAgents README-graph check, set 7 (2026-10-24)

Ten agent projects that draw (or spell out) their agent graph in the README were scanned with
`visualagents scan --static`. None of them appears in sets 1-6. Each map was scored against the README graph. The
failures were then traced to code shapes the scanner did not understand, and those shapes were fixed with general
rules on `dev-refinement`. No rule names a project. All 60 projects of sets 1-6 were re-scanned to check for
regressions.

Ground truth is in `ground_truth_set7.py`. It was written from the README diagrams before any scan. Raw scores for
main and dev-refinement are in `results-set7-2026-10-24.json`.

## How to read the numbers

- **Matching rate (node recall)**: the share of README components that appear on the map.
- **Correct rate (node precision, strict)**: the share of map blocks that are README components. The lenient
  version also accepts blocks that exist in today's code but are left out of the drawing, such as deer-flow's
  podcast and PPT graphs or MetaGPT's other roles.
- **Code recall**: matching rate leaving out drawn components the code doesn't have as agents (`readme_only`).
  Examples are OWL's web/search/coding/document "agents", which are toolkits in this repo, and DeepCode's concept and
  algorithm agents, which one planner replaced.
- **Edge recall / precision**: the share of README arrows found, and the share of map arrows that are README arrows.

## Differences per project, and why

**deer-flow.** All components were found on both versions. Main missed four arrows, all made with LangGraph's
`Command` routing:

- `goto=goto`, where the target is a variable set on several branches;
- `-> Command[Literal["research_team"]]` return annotations;
- a `Command` built in a shared helper that the researcher and coder nodes return.

*Now* all 11 README arrows are found, with precision 1.0. The strict-precision gap comes from the podcast, PPT,
prose and prompt-enhancer graphs in `src/`, plus the background-investigator and analyst nodes added after the
drawing. These are real code, so lenient precision is 1.0.

**MetaGPT.** The roles were found, but only two of the four SOP arrows were. The scanner already linked roles
through `set_actions` / `_watch`, but missed three forms:

- `_watch({WritePRD})`, a set literal rather than a list;
- `set_actions([PrepareDocuments(send_to=...), WritePRD])`, where an action is built in place;
- messages published with `cause_by=SummarizeCode`, which is how the engineer reaches QA.

*Now* 4 of 5 arrows are found. The fifth starts at "Boss", which is the user's requirement and not a role in code.
Strict precision stays low (0.19) because the repository also ships ~20 other roles: the data interpreter, the
Werewolf game, Stanford Town and so on. They are real code, but the drawing is only the software company.

**ChatDev (chatdev1.0).** Main drew none of the roles. Instead it drew the generic `ChatAgent` / `RolePlaying`
classes from the copy of CAMEL inside the repository (`camel/`). The real roles exist only as data:

- `RoleConfig.json` gives each role's prompt;
- `PhaseConfig.json` gives each phase's `user_role_name` / `assistant_role_name` pair.

*Now* the seven roles come from the phase pairs, each pair a two-way conversation (instructs / replies). The vendored
framework's classes are left off as the engine. Edge precision is 0.58 because each conversation is drawn both ways,
while the README chain gives one direction.

**OWL.** The user and assistant agents were found, but only user → assistant. The turn loop is in
`run_society(society: OwlRolePlaying)`, which calls `society.step()` in a `for _ in range(round_limit)` loop. The
scanner did not follow a method call on an annotated parameter. *Now* both directions are found. The
web / search / coding / document "agents" drawn in the README are CAMEL toolkits handed to the assistant in this
repo, not agents, so they stay off the map (code recall 1.0).

**DeepCode.** Main found the agents but no arrows. DeepCode uses mcp-agent, where an agent runs inside
`async with agent:` and is often handed to a helper (`_generate_plan_with_single_agent(planner_agent=...)`). *Now*
the run order goes from planning through reference analysis, repository download and structure generation (edge
recall 0.27, precision 0.50). Five drawn components are not in today's code:

- the concept and algorithm agents, which one planner replaced;
- phase 3's analysis, modification and refinement agents.

The code-implementation and memory agents are driven through a workflow class's helper objects that the run-order
pass does not reach yet. That is the main remaining gap.

**RD-Agent.** Main found nothing relevant, only five unrelated `*_agent` names. RD-Agent's loop types its parts with
abstract base classes and fills them in from settings:

```python
self.coder: Developer = import_class(setting.coder)(scen)
```

The subclasses reach a model only through the project's own backend: `APIBackend().build_messages_and_create_chat_completion()`.
Inside that backend, an abstract inner call is filled in per provider. The loop's step methods (`direct_exp_gen`,
`coding`, `running`, `feedback`) are run by a metaclass, never called in the code. *Now*:

- model calls are traced through project backend wrappers and template methods;
- annotated slots whose implementations ask a model become agents;
- step methods run in the order they are written and loop back.

All five README components and all five arrows are found. The quant loop's factor and model variants are separate
branches.

**VC due-diligence team.** This was already perfect on main: an ADK `SequentialAgent` of seven `LlmAgent`s. The
pipeline container and the root analyst are real extras.

**CrewAI email auto-responder flow.** Main found the crew's agents but not the flow. CrewAI Flows (`@start`,
`@listen`, `@router`) were not read at all. *Now*:

- flow steps are nodes, and `@listen(step)` / router labels are arrows;
- a step that kicks off a crew hands work to it.

The README's loop-back arrow (crew → pull emails) is a `time.sleep` and re-run outside the flow's own graph, so it
stays missed.

**ChatEval.** Main showed the AgentVerse engine classes (`LLMEvalAgent`, `ConversationAgent`). The referees are
declared in the task's `config.yaml` as an `agents:` list (name, role description, prompt), with
`order: sequential` and `max_turns: 4`. *Now* both referees and their debate turns are found, and the engine
classes are left off. Everything scores 1.0.

**AgentClinic.** The doctor, patient and measurement agents were found on main. The moderator is a plain function:

```python
compare_results(diagnosis, correct_diagnosis, moderator_llm, mod_pipe)
```

It is called by the orchestrator after the doctor's diagnosis and asks the shared `query_model` helper. *Now* a
model-calling function that the orchestrator runs beside its agents is a step of its own, named after the model it
is handed (`moderator_llm` → Moderator). Edge precision drops to 0.56: the scanner links the moderator from
whichever agent spoke last, not only the doctor.

## Changes on dev-refinement (general rules, no project named)

1. **LangGraph `Command` routing.** `goto` held in a variable, `-> Command[Literal[...]]` return annotations, and
   `Command`s built in a helper that a node returns. Routers that return `"a" if x else "b"` now give both targets.
2. **Publish/subscribe roles.** Watch sets as set literals, actions built in place, and `cause_by=` on published
   messages.
3. **Run order through objects.** A method called on a parameter annotated with a project class, or on a local built
   from one, is followed, including inherited methods. A loop wraps around only when its passes are rounds of one
   run. A loop whose index is passed to the work, or that builds a fresh object each pass, is several separate runs.
4. **Context-managed agents.** `async with agent:` runs the agent. An agent passed to a helper is that agent inside
   the helper.
5. **CrewAI Flows.** `@start` / `@listen` / `@router` steps are nodes, with arrows from `@listen` and router labels. A
   step that kicks off a crew links to it.
6. **Agents declared as data.** Two forms are read:
   - YAML/JSON `agents:` lists of named entries that carry a prompt or model, taking turns when the config's order is
     sequential or round-robin;
   - role-playing pairs (`user_role_name` / `assistant_role_name`).

   When such agents are wired, the generic classes that play them are left off. These are classes nothing hands
   work to, or that sit in a copy of a known framework inside the repo.
7. **Model calls through project backends.** A method name that exists only on model-calling classes counts as a
   model call wherever it is used. A base-class method that calls `self.k()` asks a model when a subclass's `k`
   does.
8. **Pluggable roles.** Attributes annotated with a project base class whose subclasses ask a model are agents. An
   orchestrator's uncalled step methods run in written order, and a loop class wraps around. Model backends
   (`*Service`, `*Client`, `*LLM`) are not roles.
9. **Companion model steps.** A function that builds two or more agents and directly calls a project model function
   runs a step of its own, named after the model variable it passes (`grader_llm` → Grader).
10. **Smaller fixes.**
    - `Message(role="user")` is a chat turn, not an agent.
    - The project's own invalid escape sequences no longer print `SyntaxWarning`s during a scan.

Tests: `tests/test_scan_set7.py` adds 11 made-up projects, one per rule; the full suite passes (169 passed, 5 skipped).

## Remaining failures and likely causes

- **Drawn components that are not agents in code.** This covers OWL's toolkits, DeepCode's phase-3 agents and the
  replaced concept/algorithm pair, and MetaGPT's Boss. These are README-vs-code drift, not scanner errors.
- **Large multi-product repositories.** In MetaGPT and deer-flow 1.x, strict precision is low because the
  repository ships many systems besides the drawn one. Lenient precision is 0.96–1.00.
- **Workflow classes driven through helper objects** (DeepCode's code-implementation and memory agents). The
  run-order pass follows `obj.method()` for objects it can type, but not objects built by a factory inside another
  class.
- **Conversation direction.** Role-playing pairs are drawn both ways, while READMEs often draw one direction
  (ChatDev edge precision 0.58).
- **Loops outside the code's own graph** (the CrewAI flow's sleep-and-rerun) aren't visible to static analysis.
