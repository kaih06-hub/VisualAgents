# VisualAgents README-graph check, set 6 (2026-10-22)

Ten agent projects that draw (or spell out) their agent graph in the README, none of them in sets 1-5, were scanned
with `visualagents scan --static`. Each map was scored against the README graph, the failures were traced to code
shapes the scanner did not understand, and those shapes were fixed in general rules on `dev-refinement`. No rule
names a project, and sets 1-5 were re-scored to check for regressions.

Ground truth is in `ground_truth_set6.py`. It was written from the README diagrams before any scan. Raw scores for
main and dev-refinement are in `results-set6-2026-10-22.json`.

## How to read the numbers

- **Matching rate (node recall)**: the share of README components that appear on the map.
- **Correct rate (node precision, strict)**: the share of map blocks that are README components. The lenient
  version also accepts blocks that exist in today's code but are left out of the drawing, such as TradingAgents'
  research manager or gpt-researcher's fact-checker.
- **Edge recall / precision**: the share of README arrows found, and the share of map arrows that are README arrows.

## Differences per project, and why

**TradingAgents.** On main, the four analysts were missing, and a generic `agent`/`tools`/`wrap_up` block appeared
instead. The analysts are added in a loop over a table of records (`for spec in plan.specs:
add_node(spec.agent_node, _analyst_graph(...))`), each node running a small model-plus-tools graph that a function
builds per analyst. The bull/bear and risk-team routes were also missing: they are added in a loop over node names,
with the path map kept in a module constant (`DEBATE_PATH_MAP`).
*Now*: every component is found. The remaining differences are real differences between code and drawing. In code,
the analysts all feed the bull researcher, not the whole research team. The trader hands off only to the aggressive
analyst, and the three risk analysts then debate in a cycle, which is where the lower edge precision comes from. A
research manager, absent from the drawing, judges the bull/bear debate.

**gpt-researcher (multi_agents).** All components are found on both versions. Two README arrows are missing because
the code routes through extra steps. Editor → researcher passes through the human-review node. Writer → publisher
passes through the fact-checker and visualizer, two code-only steps the README leaves out (the scorer bridges only
one).

**Voyager.** On main the map had no arrows, and the skill library was missing. Voyager's orchestrator class calls its
agents through their own methods (`self.curriculum_agent.propose_next_task()`,
`self.critic_agent.check_task_success()`). It also calls the action agent's model from outside
(`self.action_agent.llm(messages)`), with LangChain's `ChatOpenAI` called directly. None of these was recognised as
running an agent. `SkillManager` calls a model, but its name doesn't end in "Agent", so it was skipped.
*Now*: curriculum → action ⇄ critic → skill library → curriculum, with the retry loop. The extra arrows (action →
curriculum, action → skill manager) are real exits from the loop.

**Agent Laboratory.** On main the map had no arrows, and mle-solver and paper-solver were missing. The agents run
through an inherited `BaseAgent.inference()`, which calls the project's own `query_model()` helper, so the model call
is two hops away. The solvers are built as local variables (`solver = MLESolver(...)`).
*Now*: all eight components are found and the phase order is followed. Edge precision is low (0.33) because the
workflow's phases can be skipped through config flags. That makes many "phase A → phase C" arrows real in code that
the drawing does not show.

**STORM (not fixed).** Static analysis maps STORM's DSPy predictors (`write_outline`, `conv_to_section`, persona and
Co-STORM expert modules), while the README draws four coarse stages, so the map is at a finer level of detail than the
drawing. The stage classes are reached through an engine (`STORMWikiRunner.run`) that calls
`self.storm_knowledge_curation_module.research()`, and so on. Mapping that would mean grouping predictors under the
pipeline stage that owns them. That is a design change and was left for a later round.

**multi-agent-concierge.** On main the map showed a single `workflow` block. The four task agents are data records
(`AgentConfig(name=..., system_prompt=..., tools=...)`) run by one generic `speak_with_sub_agent` step, and an
`orchestrator` step picks between them. Toy agents from `video_tutorial_materials/` notebooks were also getting in.
*Now*: an exact match. The four agents and the orchestrator are found, with routes both ways. The tutorial folder is
treated like `examples/`.

**ADK small-business-loan.** On main, all five agents were found but no arrows. ADK's `AgentTool(sub_agent)` in
`tools=[...]` was not recognised as delegation (only `.as_tool()` was). The LLM-as-judge gate is an
`after_agent_callback` function that calls Gemini, and it was not on the map.
*Now*: orchestrator → four sub-agents, plus the judge gate ⇄ orchestrator. The README's sequence diagram also draws
each sub-agent's result returning to the orchestrator. Agent-as-tool is kept one-way, as it is for `.as_tool()`, so
those four return arrows are counted as missed.

**TaskWeaver.** On main the map had no arrows and showed four copies of the code interpreter. TaskWeaver ships
`CodeInterpreter`, `CodeInterpreterCLIOnly` and `CodeInterpreterPluginOnly`, plus matching generators. Its roles
never name each other: a session passes messages between them.
*Now*: the mode variants are merged into one agent, and the planner hands work to each role and gets results back.
Strict precision stays low because the optional extension roles (web search, image reader, and so on) are real code
the drawing leaves out; lenient precision is 0.89.

**Enterprise Deep Research (not fixed).** The LangGraph is found. The drawing's "ToDo Manager" is a plain state class
(`ResearchTodoManager`) that the graph does not run as a node. `validate_context_sufficiency` and `agent_executor` are
code-only steps with names that do not appear in the README.

**XAgent (not fixed).** The components are found, but no arrows. XAgent picks its agents at run time through a
registry (`agent_dispatcher.dispatch(RequiredAbilities.plan_generation, ...)`), so static reading cannot follow the
order. The `--llm` mode or live tracking is the right tool for this shape.

## What changed in the code (dev-refinement)

All of these rules are written about code shapes, not about project names. Each is covered by a made-up project in
`tests/test_scan_set6.py`.

1. **LangGraph routes and node tables** (`static_scan.py`): `add_conditional_edges` and `add_edge` now resolve a loop
   variable over node names, a path map held in a constant, and node names taken from a table of records.
2. **Per-node graph templates**: when a function builds a fresh compiled graph for each of several nodes, that inner
   graph is treated as part of each node and its inner nodes leave the map. When the function builds a graph for only
   one node, the graph is linked as a subgraph.
3. **Agent-as-tool wrappers**: `AgentTool(x)` / `AgentTool(agent=x)` count as a hand-off.
4. **Model-calling callbacks and guardrails** given to an agent are checking agents.
5. **Run order through project agent classes** (`run_order.py`, `call_sites.py`): a call to an agent object's own
   model-calling method counts as running that agent. This covers methods inherited from a base class, methods that
   reach the model through the project's helper functions, and calling an agent's model from outside it. Retry loops
   come back to their first agent, and LangChain chat models called directly count as model calls.
6. **Companion model-callers**: other model-calling parts that an orchestrator builds next to its agents are agents
   too.
7. **Record agents, mode variants, lone planner**: agents defined as config records are routed by the project's single
   orchestrator, router or triage step. Variants of one agent built for different modes are merged. When agents never
   name each other and exactly one of them is a planner or orchestrator, that one leads. `tutorial` folders are
   treated like `examples/`.

Tests: 134 passed, 4 skipped (10 new tests). One older test was updated on purpose: it now expects
`CodeGeneratorCLIOnly` as an alias of `CodeGenerator` instead of a separate block.

## Limits of this check

- These fixes were written after looking at set 6, so set 6 is no longer held out. The unchanged scores on sets 1-5
  show that nothing regressed. Whether the fixes help on new projects will only show on the next held-out set.
- gpt-researcher's architecture image is hosted as a GitHub user-attachment, which this environment could not
  download. Its ground truth comes from the step list the README writes out from that diagram. Projects whose only
  graph was an image of this kind (open_deep_research, ai-hedge-fund) were not used.
- All runs are `--static`. The LLM pass and live tracking were not measured.
